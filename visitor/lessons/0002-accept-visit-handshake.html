Visitor Pattern · Lesson 0002

The accept / visit handshake

Elements say who they are; visitors say what to do.

Your win in ~7 minutes: hand-trace shape.accept(v) → the exact visitX that runs.

The two sides

From Lesson 1: elements stay dumb, visitors hold logic. The contract, per Refactoring.Guru and Design Patterns in Action, is tiny:

interface Shape { void accept(Visitor v); }

interface Visitor {
  void visitDot(Dot d);
  void visitCircle(Circle c);
}

class Dot implements Shape {
  public void accept(Visitor v) { v.visitDot(this); }
}
class Circle implements Shape {
  public void accept(Visitor v) { v.visitCircle(this); }
}

Each accept is one line: call the visitor method named after my own class, passing this. Dot never calls visitCircle. That one-line honesty is the whole trick — MartinLwx calls it “trivial forwarding that makes the pattern work.”

Trace it (tap through)

1Client holds Shape s = new Circle() and a Visitor v = new XmlExportVisitor(). It calls s.accept(v).
2Virtual dispatch on s runs Circle.accept — not Dot.accept, not base. The element reveals its runtime type.
3Inside, v.visitCircle(this) runs. Virtual dispatch on v picks XmlExportVisitor.visitCircle. Both types are now known.

· You just simulated double dispatch; Lesson 3 explains why both steps are needed.

Rule: never call visitX from client code. Always enter through accept. Calling the visitor directly skips the first dispatch — the element never gets to say who it is.
