Visitor Pattern · Lesson 0004

When not to use it

Cheap in one direction, expensive in the other.

Your win in ~7 minutes: given a change (“new export” vs “new shape”), choose Visitor or reject it — and defend the call.

The asymmetry

From Lesson 1 through Lesson 3 you built the machine. Now price it, per Refactoring.Guru:

+New operation: cheap. Add PdfExportVisitor implementing visitDot/visitCircle. Zero edits to elements. Open/Closed holds.
−New element type: expensive. Add Rectangle → add visitRectangle to the interface → update every existing visitor. Recompile-the-world.
=Rule-of-thumb: stable types + growing operations → Visitor. Volatile types → skip it; prefer plain polymorphism.

MartinLwx sharpens it: Visitor fits compilers and analyzers because an AST is stable while analyses multiply. The reverse — new node types weekly — makes Visitor “more work than it saves.”

Two more costs

  • Encapsulation strain. Visitors often need data elements would rather keep private. You widen access or the visitor cannot do its job.
  • Temptation to cheat. An instanceof inside visit, or a base-class accept that type-checks, silently breaks the handshake. Each concrete element must override accept itself — see anti-patterns.
