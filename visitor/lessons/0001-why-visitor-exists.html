Visitor Pattern · Lesson 0001

Why Visitor exists

Add operations without reopening every class.

Your win in ~6 minutes: look at a shape hierarchy and say whether Visitor fits — before writing any Visitor code.

The mess it fixes

You have Dot and Circle. First you add draw(). Then exportXml(). Then area(). Each operation lands inside every element class, or in one giant instanceof chain:

if (shape instanceof Dot d) { /* export dot */ }
else if (shape instanceof Circle c) { /* export circle */ }
// every new operation repeats this chain

This is the expression problem: a stable set of types with a growing set of operations. SourceMaking puts Visitor's intent bluntly — define a new operation without changing element classes. Refactoring.Guru frames it the same way: separate algorithms from the objects they run on.

The Visitor move

Keep elements dumb. Put each operation in its own visitor class:

interface Shape { void accept(Visitor v); }
interface Visitor {
  void visitDot(Dot d);
  void visitCircle(Circle c);
}
// New operation = new class. Shapes never change.
class XmlExportVisitor implements Visitor { /* ... */ }
class AreaVisitor implements Visitor { /* ... */ }

Client code never type-checks. It just does shape.accept(visitor) and the right method fires — you will trace exactly how in Lesson 2.

Mission tie: every lesson serves your mission — no more instanceof chains when a new export, metric, or check arrives. See cheatsheet for the skeleton.
