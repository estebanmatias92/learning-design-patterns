Visitor Pattern · Lesson 0003

Single vs double dispatch

Why overloads alone pick the wrong method.

Your win in ~8 minutes: predict the output of v.visit(s) vs s.accept(v) — and say why they differ.

Single dispatch is all Java gives you

A virtual call like s.draw() dispatches on one runtime type: the receiver s. That is single dispatch (SourceMaking). Overloads are different: v.visit(dot) vs v.visit(circle) are chosen by the static type at compile time.

Shape s = new Dot();          // runtime: Dot, static: Shape
Visitor v = new XmlExportVisitor();
v.visit(s);                   // binds visit(Shape) — Dot-ness is lost!
s.accept(v);                  // routes to visitDot — Dot-ness recovered

Refactoring.Guru: Visitor and Double Dispatch shows this exact trap: the compiler “plays safe” with overloads and uses early binding, so visit(Shape) wins even though the object is a Dot.

Visitor = two single dispatches

1First dispatch: s.accept(v) is virtual on the element. Runtime type picks Dot.accept. Type recovered once.
2Second dispatch: v.visitDot(this) is virtual on the visitor. Inside Dot.accept, this is statically Dot, so the overload binds correctly — then dispatches to XmlExportVisitor. Type recovered twice.

No instanceof, no casts. MartinLwx: “two consecutive single dispatches produce the same effect” as double dispatch.
