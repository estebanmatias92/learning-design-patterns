Visitor cheatsheet

The compressed essence of Lessons 1–4. Revisit this, not the lessons.

Skeleton (Java)

interface Shape { void accept(Visitor v); }

interface Visitor {
  void visitDot(Dot d);
  void visitCircle(Circle c);
}

class Dot implements Shape {
  public void accept(Visitor v) { v.visitDot(this); }
}
class Circle implements Shape {
  public void accept(Visitor v) { v.visitCircle(this); }
}

class XmlExportVisitor implements Visitor {
  public void visitDot(Dot d) { /* export dot */ }
  public void visitCircle(Circle c) { /* export circle */ }
}

// Client: never type-checks
for (Shape s : shapes) s.accept(new XmlExportVisitor());

Dispatch in two lines

1s.accept(v) — virtual on element. Picks Dot.accept vs Circle.accept.
2v.visitDot(this) — virtual on visitor. Picks XmlExportVisitor.visitDot. Overload binds because this is statically Dot.

Rules

  • Enter through accept only. Never call visitX from client code.
  • Every concrete element overrides accept itself; no base-class instanceof.
  • Prefer named visitDot over overloaded visit(Dot) — grep-friendly, mis-wiring fails loudly.
  • Make visitor methods pure-virtual / abstract — a forgotten override must not compile silently.

Costs

  • New operation: +1 visitor class, 0 element edits. Cheap.
  • New element type: +1 visitX on interface + update every visitor. Expensive.
  • Fit: stable types, growing operations (compilers, ASTs, document models). Volatile types → plain virtuals.
